# 执行者–审核者代码协作机制（CRDocs）

`CRDocs` 是 `StepModelCompare` 正式平台（`Platform/`）开发阶段中，执行者（Executor）与独立审核者（Reviewer）的长期代码审查交接面。开始代码开发或审查前，必须读取本文件、`RULES.md`、`STATUS.md`、`REVIEW.md`、`IMPLEMENTATION.md` 和 `DEFERRED.md`。历史审核不在活动文件中无限追加，统一通过 [`archive/INDEX.md`](../INDEX.md) 查找。

## 活动区与归档区

| 区域 | 规则 |
| --- | --- |
| `STATUS.md` | 只记录当前代码任务的状态、分支、范围、结论、证据边界和下一步；附最近 3 轮状态索引。 |
| `REVIEW.md` | 只保留当前任务最近 3 轮独立审核/整改交接，按最新在前排列。 |
| `IMPLEMENTATION.md` | 只保留当前任务最近 3 轮执行记录、验证命令输出摘要和未验证边界。 |
| `DEFERRED.md` | 只保留仍然有效的延期项与验收条件；已关闭或仅属于历史任务的条目随该任务归档。 |
| `archive/<日期>_<任务或阶段>_<审核内容概要>/` | 存放超过 3 轮或已切换任务的完整历史；目录内必须有 `INDEX.md`，原始 Markdown 文件与索引一起保存。 |

“一轮”是一次独立代码审核及其对应的执行者整改/交接记录；同一轮涉及多个文件算一轮，不按文件数重复计算。当前开发任务切换时，旧任务的全部活动记录先归档，再建立新任务的活动记录。

## 归档流程（硬规则）

1. 在活动文件新增第 4 轮之前（或切换至新任务前），先把最旧的一轮（或旧任务）完整内容移入新建归档目录；不得直接删除或覆盖历史。
2. 归档目录命名为 `YYYY-MM-DD_<任务或阶段>_<审核内容概要>`，例如 `2026-12-01_STEP-PLAT-001_后端骨架与OCCT进程池收口`。
3. 归档目录内必须有 `INDEX.md`，列出任务编号、轮次、结论、日期、原始文件和检索关键词；根目录 [`archive/INDEX.md`](../INDEX.md) 必须同步增加入口。
4. 活动区只保留可直接指导下一步的内容。历史问题、原始命令输出和完整逐项证据以归档文件为准；活动文件通过相对链接指向归档，不复制整段历史。
5. 归档后检查活动区行数、链接、状态和 `git diff --check`。不得因压缩历史而改变审核结论、问题 ID、延期条件或验证边界。

## 执行者（Executor）

1. 读取 `STATUS.md`、`REVIEW.md`、`DEFERRED.md` 和相关归档索引。
2. 只处理当前任务范围或仍为 `OPEN` 的审核问题，不擅自扩大范围，不改动冻结的 `Demo/` 目录。
3. 严格遵守 `.claude/Rules.md` 第 7 节（全中文注释、最小实现、1000/1500 行数门禁、不建垃圾桶模块）修改代码，并执行对应的单测、并发/集成测试、语法、行数检查与 `git diff --check`。
4. 把本轮改动文件、核心设计说明、实测命令与结果、未验证边界写入 `IMPLEMENTATION.md`；若会超过 3 轮，先归档最旧轮次。
5. 把 `STATUS.md` 更新为 `READY_FOR_REVIEW`。**执行者不得自行写入 `APPROVED`**。
6. 不修改审核者已经写出的结论；如有技术异议，写入本轮实施记录说明依据。

## 审核者（Reviewer）

1. 读取 `STATUS.md`、`IMPLEMENTATION.md`、`DEFERRED.md`，必要时按索引追溯归档与 `Docs/` 设计基线。
2. 必须独立检查实际源码、SQL 事务/并发边界、跨企业隔离守卫、diff、调用链和必要的独立测试命令，不以执行者文字说明替代一手证据。
3. 默认只审核，不直接修改业务代码；仅在用户明确授权时修复代码。
4. 把结论、P0/P1/P2 分级问题（附稳定问题 ID，如 `PLAT-001-P0-1`）、复核证据和边界写入 `REVIEW.md` 顶部；新增第 4 轮前先归档最旧轮次。
5. 已修复问题标记 `RESOLVED`，不在后续轮次重复提出；未来阶段或真实客户环境验证项转入 `DEFERRED.md`。
6. 仍有 P0/P1 时将 `STATUS.md` 置为 `REJECTED`；当前范围闭环且无未解 P0/P1 时才置为 `APPROVED`。

## 状态和问题词汇

- 任务状态：`IDLE`、`READY_FOR_REVIEW`、`REJECTED`、`APPROVED`、`BLOCKED`、`SUPERSEDED`。
- 问题结论：`OPEN`、`RESOLVED`、`DEFERRED`、`WONT_FIX`。
- `APPROVED` 只代表 `STATUS.md` 明确写出的代码范围与实测证据通过，不代表整个项目、客户真实 STEP 样本集或生产部署环境已验收。

## 不可突破的协作约束

- 稳定问题 ID 不得跨轮改名；设计文档、已采纳决定（`STEP-SIM-004/005`）与代码不一致时先指出偏差，不为迁就实现而偷偷降级安全/并发/隔离契约。
- 严格执行单文件 `1000` 行预警与 `1500` 行硬上限门禁；P2 与环境受限项不阻断当前切片时登记至 `DEFERRED.md`。
- 所有 SQLite 替代测试、Mock 桩或 `Demo/` 自制样例结果必须明确标注，**绝不能写成** PostgreSQL 并发实测或客户真实 STEP 实测通过。

## 用户最简提示词

- 给执行者：`读取 CRDocs，按 REVIEW.md 修改；完成后自测并按规则交接。`
- 给审核者：`读取 CRDocs，独立审核当前任务；回写 REVIEW.md 和 STATUS.md；超过 3 轮时先归档最旧轮次，并给出下一步提示词。`
