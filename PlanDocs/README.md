# STEP 模型检索与数据复用项目 · 方案审核交接

本目录用于决定本项目的范围、技术路线、实施顺序及验收口径。用户负责决定是否采纳，提案方和审核方轮流交接。当前话题以 STATUS.md 为准。每份提案、审核、决定都标注话题编号，讨论中的指标和排期均为建议值。

## 阅读入口和文件归属

| 文件 | 谁写 | 开始前怎么用 |
| --- | --- | --- |
| README.md | 用户或用户授权方 | 双方先读本规则 |
| STATUS.md | 当前交棒方 | 双方确认话题、轮次、状态和下一位负责人 |
| PROPOSAL.md | 提案方 | 审核方据此独立核查需求、论据和验收设计 |
| REVIEW.md | 审核方 | 提案方读与当前话题和轮次匹配的意见，逐条回应 |
| DECISIONS.md | 用户明确指定的收口方 | 只引用本项目已采纳的决定 |

本项目使用 STEP-SIM- 开头的话题编号。目录迁入时已有的 DIR- 系列决定、FIX-EXPORT-SAFETY-PLAN.md、use.txt 和旧归档提示属于来源项目。它们保留历史上下文，本项目按本 README 操作。源码、样本或客户制度尚未提供时，在「未核实」列出所需证据及其对决定的影响。

## 提案方

1. 读取 README.md、STATUS.md、REVIEW.md。开始新话题或回应修改请求时将状态设为 PROPOSING。新话题从第 1 轮开始，回应实质修改请求时轮次加一。
2. 将本轮完整方案写入 PROPOSAL.md，使用下面七个二级标题。第一轮在最后一节写「无」。后续轮次对每条意见注明采纳、部分采纳或不采纳，并写出依据和改动位置。
3. 将 STATUS.md 设为 READY_FOR_REVIEW，交给独立审核方。提案方只维护提案和交接状态，README.md 的变更须获用户授权。

~~~text
## 要决定的问题
## 建议决定
## 证据
## 未核实
## 建议顺序
## 明确不做
## 对上一轮审核的处理
~~~

## 审核方

1. 读取 README.md、STATUS.md、PROPOSAL.md，并查阅同一项目已采纳决定的标题和未决假设。根据文件独立判断。
2. 区分客户原始要求、资料可证实的能力、方案假设、实测结果。技术事实优先核对一手资料或实物，仓库结论注明路径和搜索范围。仅能通过客户样本验证的结论写明验证方法。
3. 重点核对候选漏检、相似但不可复用的反例、验收分母，以及平台投入的前提。建议修改时写清会影响哪项交付，并给出最小修正。
4. 使用以下标题写入 REVIEW.md，标明话题和轮次。同步更新 STATUS.md，写明下一位负责人。保留提案方原文。

~~~text
## 本轮核对了什么
## 属实
## 不成立或说重了
## 遗漏
## 顺序
## 未核实
## 结论
~~~

「顺序」写「不改」或调整后的完整顺序。存在影响下一步的实质问题，结论为 CHANGES_REQUESTED；能按提案启动下一步，结论为 CONVERGED。欠缺决定性证据且无法推进时，结论为 BLOCKED，并指出需要谁提供什么。最多三轮，第 3 轮结论只能为 CONVERGED 或 BLOCKED。

## 状态与采纳

通常从 IDLE 进入 PROPOSING，再交到 READY_FOR_REVIEW。审核后按结论转入 CHANGES_REQUESTED、CONVERGED 或 BLOCKED。修改后重新交审；遇到阻塞则由 STATUS.md 指定的负责人补证据。CONVERGED 之后等用户明确采纳。

用户确认收口后，指定方将日期、话题编号、决定、执行顺序、未决假设和定稿路径写入 DECISIONS.md，标记 ADOPTED。开始下一题前将定稿和对应审核保存在本目录按话题编号命名的归档中，核对决定所指路径，再将状态置为 IDLE。项目记忆按用户全局指令和实际存在的项目规则管理。

## 用户交接用语

给审核方：「读取 PlanDocs/README.md、STATUS.md 和 PROPOSAL.md，独立审核当前话题，按规则写入 REVIEW.md 并更新 STATUS.md。」

给提案方：「读取 PlanDocs，按当前轮 REVIEW.md 修正提案并交接。」

确认采纳时：「讨论已收敛，按 PlanDocs 规则记录本次决定。」
